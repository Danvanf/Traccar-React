# TODO: Make device protocol profiles the telemetry authority

## Goal and current data flow

Traccar supplies positions and an `attributes` object with keys such as `io50`. Keep the received record intact. For every display or translated export, resolve the profile assigned to the record's device/vehicle, translate each known key to a label and physical value, then apply the user's display units. Preserve the raw key and value for diagnostics and raw exports. An unknown key may show `io1234`, but should be marked unmapped; it must not silently acquire a meaning from another device's profile.

The current FMM003 is the first profile to verify, not a reason to hard-code Teltonika behavior in consumers. The frontend reads positions from Traccar's HTTP API (`src/lib/traccarApi.js`, for example `GET /api/positions`); `TraccarScope.Api` uses its configured `ConnectionStrings:TraccarScopeApi` for the app's catalog and reports. Traccar stores the position data behind that HTTP API, but this app does not query Traccar's database directly. Use the Traccar API response as the decoder contract. Some fields are already decoded or use non-metric conventions (for example, position speed is handled as knots here), so don't assume every attribute is an unscaled metric number.

## Implemented so far

- Vehicle Catalog profile assignments now drive graph groups, the status card, selected-trip map details, and translated range exports. Missing or unassigned profiles are visible instead of silently selecting a default.
- Graph pressure conversions/labels and telemetry report conversions now use profile definitions. Report fields use stable `quantity` tags; displayed values include the profile's units. Graph auto-scaling remains a plot-only transform.
- Vehicle Health and Tracker Health resolve the profile from the vehicle represented by each telemetry window. Their rows and CSV exports now name the profile used; missing or unavailable profile assignments produce an explicit warning and show profile-mapped metrics as unavailable.
- Vehicle Health and Tracker Health now load all device bindings and resolve the vehicle effective at each telemetry window's start time. The active-only `/api/device-bindings` endpoint remains unchanged for live UI contexts; `/api/device-bindings/history` serves closed and active intervals for historical reports.
- Selected-trip map details and trip telemetry graphs now pass the trip start time into the shared resolver, so a moved Traccar device uses the vehicle binding effective for that trip. A protocol profile belongs to a vehicle and may be assigned to multiple vehicles; it is not a one-profile-per-device relationship.
- `translateAttribute()` is the shared pure read-time translator for graph values, status fields, map details, range CSV, telemetry export, and report metrics. It carries the raw value, translated value, label, unit, quantity, source, and missing/invalid/sentinel status.
- Profile mappings can carry `sourceUnit`, `canonicalUnit`, `canonicalScale`, `canonicalOffset`, `quantity`, and `precision`. Translation now returns the numeric display value and canonical value separately for fields using this metadata. Profile schema 7 migrates matching older default-profile mappings with a browser backup. Except for captured `io50` kPa, the new unit declarations preserve existing catalog/profile assumptions and still need validation against Traccar samples or known values. Unverified/ambiguous fields remain on their existing mapping path.
- Shared telemetry snapshots save each channel's label and unit alongside translated point values, so the public view does not depend on the creator's local profile JSON.
- Telemetry CSV attribute cells use the selected profile's translated value; its metadata records profile-decoded/raw-unmapped status, output units, source/canonical units when supplied, quantity, conversion, precision, source group, AVL ID, and sample timing. CSV cells remain native-time samples with no interpolation. The range export also preserves raw `raw_attr_*` columns in translated mode; raw Teltonika mode keeps source keys and values.
- Profile definition schema 16 incorporates the 2026-10-16 official FMM003/FMM00A reference review. Engine Load is confirmed, AVL 12/13 use documented GPS fuel interpretations with separate raw/decoded scales, and unchanged unsupported CAN-ID guesses are removed. Custom edits and recorded historical revisions are preserved. See [the shared reference and reuse design](TELTONIKA_FMM003_FMM00A_AVL_REFERENCE.md). The prior sample-only uncertainty is superseded by this manufacturer/decoder review.
- All current devices are FMM003. The sample supports `io50` as kPa and `io51` as millivolts; keep their kPa-to-inHg and mV-to-V conversions. It did not include alternate IDs `io100`, `io101`, `io138`, `io388`, or `io529`, so those aliases remain catalog-derived rather than sample-verified.
- General display units now have a saved, user-level Imperial/Metric preference in Settings. It flows through profile-driven telemetry values, graphs and cursor legends, trip/history summaries, map details and speed bands, event measurements, reports, and CSV/JSON exports. GPS speed, distance, altitude, and accuracy export columns use the selected system. Canonical conversion metadata now covers selected common mappings; only the captured `io50` kPa source is sample-confirmed, while the other unit declarations retain catalog/profile assumptions pending sample validation. Per-quantity choices (such as barometric pressure in inHg while otherwise Metric) remain future work.
- The live status card's source key, label, and units now come from each profile mapping's `statusCardField`; its settings checkboxes use the assigned profile's labels. Schema 7 migrates the former hard-coded FMM003 rows and preserves saved `fuelUsed`/`fuelRate` selections as raw `AVL 12`/`AVL 13` fields. Graph descriptions for ignored data elements also use profile labels.
- Vehicle Health and Tracker Health value headers use the mapped profile labels when a report has one label for that metric; metric values and units come from the profile translator. Mixed-profile reports retain a stable semantic header when labels differ.
- Device profile definitions are now stored as distributable JSON files in `device-profiles/`. The frontend build discovers and bundles every `*.json` there; new IDs are merged into existing local/shared definitions only when absent, preserving user edits. The existing default definition was moved intact to `teltonika-fmm003.json`; its legacy ID remains unchanged so vehicle assignments continue to resolve. See `docs/DEVICE_PROTOCOL_PROFILES.md` for installation and authoring instructions. This packages the repository baseline, not any unverified browser/database edits; uncertain FMM003 conversions remain in Human ToDo.

## Known limits and design decisions

1. **Historical profile resolution is partly implemented.** Vehicle Health and Tracker Health use `/api/device-bindings/history` at each report window's start time; selected-trip map details and graph groups use the same time-aware resolver. Vehicle profile assignments now use an append-only, effective-dated history resolved per telemetry timestamp. Existing assignments receive a legacy baseline at vehicle creation time because the original assignment date is unavailable. Live UI contexts resolve the assignment effective now; `/api/device-bindings/nearest` remains a repair heuristic, not a time-valid decoder. Range CSV now refuses translated exports that span multiple profile assignments; separate per-profile files could improve this workflow. Restart the API to create the history table and baseline rows, then validate reassignment against historical trips.
2. **Shared profile definitions use the existing Traccar Scope API table.** New API routes let active users read definitions and limit edits/deletes to administrators. The profile editor synchronizes changes and preserves a backup when local and shared versions conflict. Apply `scripts/phase_telemetry_profile_schema.sql` after Phase 3 DDL; localStorage remains the fallback if server storage is unavailable. Confirm the production schema is current and add stricter edit-conflict handling if profiles later need per-user edits. Shared links save labels, units, and translated values as a snapshot.
3. **Graph conversion overrides were removed.** Graph values and labels use the assigned profile, and the plotted scale is kept separate from physical values. `translateAttribute()` centralizes read-time decoding across the main UI consumers. The General Imperial/Metric preference is implemented; completing canonical mappings and per-quantity preferences remains open.
4. **Status card mappings are profile-driven.** Profile JSON defines source attributes, labels, and units. Stable status-field IDs remain as user preference keys; their display labels and source mapping come from the assigned profile.
5. **Report and export boundaries need continued review.** The selected-trip map popup and health reports use profile mappings. Range and telemetry exports use the selected profile and display preference; telemetry metadata documents decoded channel units and mappings. The track-only export contains place roles, timing, and route distances, so it does not decode telemetry channels. Backend reports still do not receive browser profile definitions; decide whether each report should use a shared server-side profile or remain GPS/trip-only before adding telemetry fields.
6. **Saved profile loads migrate with a backup and notice.** The local storage envelope is version 3; individual profile definitions are at schema version 14. The migration keeps AVL 12/13 unconverted because their configured meanings are unknown, adds explicit text/identifier value types and rejects invalid canonical numeric input, adds documented trip-odometer and BLE fields, the tentative AVL 31 label, GSM Area Code `io206`, SIM ICCID halves `io11`/`io14`, Network Type `io237`, and Trip Status `io250` only where mappings are absent, and preserves user edits. It also moves status-card source keys into profile metadata and removes obsolete per-field confidence labels/notes. `validateAttributeMap()` validates quantity, source/canonical units, canonical scale/offset, status-card field, and precision. Canonical conversion is implemented for selected common FMM003 mappings; other fields still use existing mappings.
7. **Traccar model controls attribute names.** The 2026-10-08 test capture reported Traccar 6.14.5 and device model `null`, so the positions use raw `ioN` keys. In that Traccar version, configuring `FMM003` activates model-specific handlers that emit normalized names such as `fuelUsed`, `fuelConsumption`, `engineLoad`, `coolantTemp`, `rpm`, and `batteryLevel`; `io206` is handled as `lac`. Do not change the Traccar model setting until the assigned profile and translator support both the raw and normalized key paths and tests cover them. This is Traccar decoder behavior, not manufacturer evidence that a particular vehicle has each AVL field configured.

## Debugging checklist

Start with one Traccar position's `attributes` JSON and follow its device ID, vehicle binding, `profileId`, profile version, source key, decoded value, display unit, and plot factor through the UI. Log these stages in development without changing stored records. If a label or number differs, check whether the consumer selected the wrong profile, an old browser-local definition was merged, Traccar pre-scaled the value, a consumer has hard-coded conversion, or the graph applied a visual factor. Fix the responsible stage rather than adjusting the label to match a bad number.

## Visual Device Protocol Profile Editor: screen design

Build a visual editor for the *selected profile's current field-mapping JSON*. In Settings → Device Protocol Profile Editor → Field Mappings, add **Open Field Mapping Editor** beside the JSON textarea. The attached FMM003 JSON is the user's current snapshot and is a layout example, not a replacement for the saved definition. It differs from the bundled profile: for example, `io12` says Fuel Used with `litersToGallons`, `io44` uses `tenthsToNumber` to `kPa`, `io45` uses `timesTen` to `kPa`, and `io50` is raw `kPa`.
